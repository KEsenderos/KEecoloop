1\. 目的とスコープ

外国語の音声ファイルの「指定した数秒の区間」を何度も繰り返し聞き、耳を慣らすためのiPhone用アプリを作る。個人利用のみ、費用0円で運用する。

1.1 範囲内

- 音声ファイルの選択（Googleドライブから一度iPhoneに保存し、「ファイル」アプリ経由で選ぶ）

- 指定区間の無限リピート再生

- 再生／一時停止／停止／区間移動の操作

- 倍速再生（1.2・1.1・1.0・0.9・0.8倍の5段階のボタン。声の高さは変わらない）【v2.2・v2.3】

- 画面を消した状態での再生継続（ロック画面からの操作を含む）

- オフラインでも起動できること（音声ファイルは端末内に読み込んだ後は通信不要）

1.2 範囲外（今回は作らない。勝手に追加しないこと）

- 5段階以外の再生速度の設定（スライダー、自由入力など）、波形表示、操作できるシークバー（見るだけの区間バーは範囲内）

- プレイリスト・複数ファイル管理・お気に入り

- アプリ内でのファイル保存（読み込むたびに選び直す）

- 他人への配布、ログイン、サーバー側の処理、データ収集

- 音声ファイルのアップロード（音声ファイルはネット上に置かない）

4.2 入力欄のルール

- 移動時間の数字入力の確定は change イベント（欄を離れる／Enterキー）で行う。1文字ごとには処理しない。（開始・終了の時間は文字入力をしない。v1.6）

- ▲▼ のタップ表示（v2.0）:
  ▲▼ に触れた瞬間（pointerdown）に、ボタンの色をアンバー（--accent）に変え、字・矢印を暗い色（--accent-ink）にする（CSSのクラス名 pressed）。指を離したら（pointerup／pointercancel／pointerleave）元の色に戻す。ただし一瞬のタップでも色の変化が見えるよう、触れてから最低 PRESS_MIN_MS（150ms）は色を保つ。iPhoneのSafariは :active だけでは確実に色が変わらないため、JavaScriptでクラスを付け外しする。

- 開始地点・終了地点の桁ごとの ▲▼（v1.6）:
  1回タップするごとに、その桁の単位（10分・1分・10秒・1秒＝600・60・10・1秒）だけ時間を足し引きする。桁の繰り上がり・繰り下がりあり（例: 00:59 の1秒の ▲ → 01:00）。範囲の端を超える場合は端の値に止める（範囲は5.3）。止まっても、何も表示しない。長押しの連続動作は作らない。

- 入力欄に打った直後に「再生・停止・区間移動」を押したときは、先に入力を確定（blur）してから動作する。【v1.5】

- 移動時間の−／＋ボタン:
  1秒ずつ変える。1と60で止まり、メッセージは出さない。数字の直接入力（下）と同じ処理を行う。

- 移動時間:
  整数のみ。小数は四捨五入。1未満は1、60超は60に補正しメッセージ表示。数字以外は元の値に戻してメッセージ表示。

- ファイル未選択の間は、再生・停止・区間移動・開始・終了の桁の▲▼・移動時間をすべて無効（disabled）にする。

5.2 用語と計算

- 内部の時間は全て「秒（小数可）」で保持する。画面表示のときだけ mm:ss
  に変換（小数は切り捨て）。

- durationSec = ファイル全長（秒）。startSec =
  開始地点（整数秒）。moveSec = 移動時間（整数）。

- endSec = 終了地点。ユーザーが桁の▲▼で決める。ファイル読込直後は min(END_DEFAULT_SEC, durationSec)。常に startSec < endSec <= durationSec を保つ。自動・手動の区別はない。**【v1.7で変更】**

- moveSec = 移動時間（整数1〜60）。リピートする区間の長さには関係せず、区間移動の進み幅の基準になるだけ。

- stepSec（区間移動の進み幅）= max(moveSec − OVERLAP_SEC, 1)。OVERLAP_SEC = 1。区間移動では、startSec と endSec のそれぞれを OVERLAP_SEC（1秒）戻してから moveSec 進める。結果は、両方に stepSec を加えるのと同じ。前の区間の最後の1秒を次の区間の頭に重ね、前後のつながりを分かりやすくするため。**【確定】** moveSecが1のときは、戻して進めると 0秒（動かない）になるため、例外として進み幅を1秒とし、重ならない。画面の説明文にもそう表示する。**【注記】**

- 区間 = startSec 以上 endSec 未満。

- rate = 再生速度（倍速）。RATE_OPTIONS（1.2／1.1／1.0／0.9／0.8）のどれか。初期値 RATE_DEFAULT（1.0）。区間の指定・表示（startSec・endSec・現在位置・区間バー）はすべて「音声ファイル上の時間」で、倍速の影響を受けない。倍速で変わるのは、実際に聞こえる時間の長さだけ（区間5秒なら、1.2倍で約4.2秒、0.8倍で約6.3秒でひと回り）。倍速でも声の高さは変わらない。倍速を使えるのは、区間の長さ（endSec − startSec）が STRETCH_MAX_SECTION_SEC（180秒）以内のときだけ（長い区間を伸び縮みさせると、処理に時間がかかるため）。1.0倍は区間の長さに関係なく使える。【v2.2・v2.3】

5.4 ロック画面・コントロールセンター（Media Session API）

- 再生中はロック画面にファイル名を表示（title=ファイル名、artist=アプリ名）。

- play／pause／stop
  の操作を、画面ボタンの再生／一時停止／停止と同じ動作にする。

- 「次へ（nexttrack）」を「区間移動」に割り当てる。ポケットの中から操作できるようにするため。**【確定】**

- 操作の登録は、起動時・ファイル読込完了時（メタデータ設定の直後）・再生開始時の3回行う。iOSは音声が読み込まれる前の登録を無視することがあり、起動時の1回だけだと「次へ」ボタンが消えるため。何度登録し直しても害はない。**【v1.2で追加】**

- 外部操作（ロック画面・イヤホン・インカム）の扱い【v1.9】:
  - play／pause のどちらが届いても、アプリの実際の状態で切り替える（再生中なら一時停止、それ以外なら再生）。iOSが状態を取り違えて逆の命令を送ることがあるため。
  - stop は、再生中なら一時停止として扱う。それ以外なら通常の停止（5.3）。
  - 直前の外部操作から REMOTE_DEBOUNCE_MS（300ms）以内に届いた操作は無視する（1回の押下が2回届く機器があるため）。
  - 一時停止中は、無音audioを鳴らし続ける（5.5）。止めると、iOSがこのアプリを再生中のアプリから外し、リモートの再生ボタンが届かなくなる。

- previoustrack・seekto・seekbackward・seekforward は登録しない。

A案の監視処理のイメージ:

> // 25msごと (RE.Config.TICK_MS)
>
> if (audio.currentTime \>= endSec - RE.Config.EARLY_JUMP_SEC) {
>
> audio.currentTime = startSec;
>
> }

B案のループ設定のイメージ:

> src = ctx.createBufferSource();
>
> src.buffer = audioBuffer;
>
> src.loop = true;
>
> src.loopStart = startSec;
>
> src.loopEnd = endSec;
>
> src.connect(ctx.destination);
>
> src.start(0, offsetSec); // offsetSec は再生開始位置（秒）

B案の倍速（v2.2・v2.3）: 声の高さを保つため、AudioBufferSourceNode の playbackRate は使わない（playbackRate は速度と一緒に声の高さも変えてしまう）。代わりに、次の方式にする。

- rate が1.0のとき: 今までどおり。元の音声（buffer）に loopStart=startSec、loopEnd=endSec を設定してループする。
- rate が1.0以外のとき: 区間（startSec〜endSec）だけを RE.Stretch.render で伸び縮みさせた短い音声（stretched。長さは「区間の長さ ÷ rate」秒、高さは元のまま）を作る。それを src.buffer にして、src.loop=true、src.loopStart=0、src.loopEnd=stretched.duration でループ再生する。src.playbackRate は常に1.0。
- stretched は、(startSec, endSec, rate) が前回と同じなら作り直さず再利用する（Engine内の変数 stretchedKey_ と stretched_）。区間や rate が変わったとき、およびファイルを選び直したときは破棄して作り直す（メモリ節約のため、保持は1つだけ）。
- 区間を変えたとき（setSection）は、再生中でも rate≠1.0 なら作り直してから、新しい再生元（createSource_）に切り替える。作り直しは同期処理で、区間5秒ならパソコン上で約0.1秒、180秒なら約2秒が目安（実測。iPhoneではそれ以上かかることがある。処理中は画面が一瞬止まる）。

位置の換算: 再生位置（pausedPos、State、画面表示）は、すべて「元の音声上の時間」で持つ。rate≠1.0のときだけ、再生元に渡す開始位置と、現在位置の計算で換算する。

> // 再生開始時（rate≠1.0）: 元の音声上の位置 offset を、stretched 上の位置へ換算する
>
> offsetS = (offset - secStart) / rate;
>
> src.start(0, offsetS);
>
> segCtx = ctx.currentTime; segOffsetS = offsetS;
>
> // 現在位置（getPositionSec, rate≠1.0）
>
> runS = segOffsetS + (ctx.currentTime - segCtx);
>
> pos = secStart + (runS % stretched.duration) * rate;
>
> // rate==1.0 のときは従来の式: secStart + ((segOffset - secStart) + (ctx.currentTime - segCtx)) % len

換算を忘れると、位置表示・区間バー・一時停止からの再開位置がずれる。rate を変えるとき（Engine.setRate）は、再生中なら現在位置を保存してから切り替える（実際の切り替えは、続く playFromStart で行う）。

伸び縮みの方法（RE.Stretch.render。WSOLA）:

1. 入力: buffer（元の音声）、startSec、endSec、rate。出力: AudioBuffer（元と同じチャンネル数・サンプリング周波数。長さ outLen = round((endSec − startSec) × sampleRate / rate)）。
2. 区間のサンプルだけを使う（区間の外は無音として扱う）。探索用に、全チャンネルを平均した1チャンネルの波形 mono を作る（計算を軽くするため、STRETCH_DECIMATE 個おきの間引き波形 monoD を使って似ている位置を探す）。
3. 1フレームの長さ N = round(STRETCH_FRAME_MS / 1000 × sampleRate)（偶数にする）、出力の送り幅 Hs = N / 2、入力の送り幅 Ha = Hs × rate。窓は周期ハン窓（50%重ねで合計が1になる）。
4. 出力フレーム k（k = 0, 1, 2 …）ごとに、入力側の目安位置 p = round(k × Ha) の前後 ±S（S = round(STRETCH_SEARCH_MS / 1000 × sampleRate)）の範囲で、「前に選んだ位置 prev から Hs 進んだ位置のフレーム」に最も似ている位置 q を探す（monoD 上の正規化相互相関が最大の位置）。k = 0 のときは q = p（探索なし）。
5. 全チャンネルについて、位置 q から N サンプルを切り出して窓を掛け、出力の位置 k × Hs に足し込む（オーバーラップ・アド）。prev = q とする。
6. 出力が outLen に達するまで繰り返す。範囲外の読み取りは0。最後に outLen で切る。

> RE.Stretch.render(ctx, buffer, startSec, endSec, rate) → AudioBuffer

B案では、再生中に loopStart/loopEnd
を書き換えるとループ範囲が即時に変わる。位置は「経過時間から計算」する（ctx.currentTime
と再生開始時刻の差を、ループ長で剰余して求める）。

5.8 更新のお知らせ（v2.4）

- 仕組み: 利用者の iPhone は、アプリを開くたびに sw.js を取りに行き、中身（CACHE_VERSION）が変わっていれば、新しい版をバックグラウンドで取り込む（sw.js は install で skipWaiting、activate で clients.claim を行う。9.7章）。取り込みが終わって新しい版に切り替わると、ページ側で navigator.serviceWorker の controllerchange が起きる。
- 帯を出す条件: 起動時に navigator.serviceWorker.controller があった（＝すでに前の版のサービスワーカーが働いていた）場合に限り、controllerchange を受けたら、UI.showUpdateBanner() を呼ぶ。初めて開いたとき（controller なし）は、帯を出さない。
- 帯をタップしたとき: location.reload() で再読み込みする（再生は止まり、選んだファイルは選び直しになる）。自動での再読み込みはしない。
- 開きっぱなしのアプリへの対応: visibilitychange で前面に戻ったとき、Date.now() − 前回確認時刻 ≥ UPDATE_CHECK_MIN_MS なら、registration.update() を呼んで、新しい版がないか確認する（失敗しても何もしない）。
- 帯は一度出たら、再読み込みするまで消さない（タップ以外の操作では消えない）。
- 公開する側の約束: 更新のたびに、APP_VERSION と CACHE_VERSION を同じ新しい値にする。値が変わらないと、新しい版と認識されず、帯は出ない（15.8）。

  のみ（REは内部用の短い名前で、アプリ名とは無関係。変更しない）。ファイル・関数・変数・id・定数は本書の名前を一字一句そのまま使う。

  RE.○○.関数名（末尾に_なし）。そのファイル内だけで使う関数は関数名の末尾に

  MOVE_SEC_MAX）、変数・関数はlowerCamelCase。

  txt-message へ）。

- 仕様にない機能・部品・見た目の追加をしない。仕様が曖昧なときは推測で実装せず、確認事項として報告する。

- 各ファイルの先頭に「ファイル名・役割・版」のコメントを書く。

- 納品前に構文チェック（例: node --check）を行う。

10\. エラー処理方針

- 読込失敗・未対応形式: MSG.FILE_ERROR
  を表示。メモリ節約のため、直前のファイルは破棄され、ファイル未選択の状態に戻る。

- 再生の開始がiOSに拒否された場合:
  MSG.PLAY_BLOCKED。状態はSTOPPED/PAUSEDのまま。

- 想定外の例外: 画面が固まらないよう try/catch で捕捉し、状態を STOPPED
  に戻して MSG を表示。console.error にも出す。

- localStorageが使えない場合:
  保存を諦めて既定値で動作する（エラー表示なし）。

- 対応形式:
  mp3・m4a**【確定】**。wavは動作しても保証しない。それ以外（flac、ogg等）は対象外。

11\. iPhone特有の注意点（実装するAI・運用者向け）

- ファイル選択の最初の操作（再生ボタン等）はユーザーのタップ操作の中で実行する。自動再生はiOSにブロックされる。

- iPhoneの「ファイル」アプリでGoogleドライブを選ぶには、Googleドライブアプリのインストールと、「ファイル」アプリでの有効化が必要（15章の手順）。

- Googleドライブ上のファイルは、選択時にiPhoneへ一時ダウンロードされる。大きなファイルは読み込みに時間がかかるので
  MSG.FILE_LOADING を出す。

- 選んだファイルは URL.createObjectURL で扱う。新しいファイルを選ぶ際は
  URL.revokeObjectURL で古いものを解放する（A案）。

- ファイル選択の\<input type="file"\>にaccept属性（例
  audio/\*）を付けない。iPhoneのSafariでは、付けるとGoogleドライブ上のmp3・m4aが灰色になり選べないことがある。

- ホーム画面から起動したPWAは、Safariと別の保存領域・別のバックグラウンド動作になる。必ず両方で検証する。

- 更新しても古い版が表示される場合は、サービスワーカーのキャッシュが原因。CACHE_VERSIONを上げる（15.8）。

- 倍速（v2.2・v2.3）は、声の高さを保つため、playbackRate ではなく RE.Stretch で作った伸び縮み後の音声を再生する。区間をまるごと一度に作るので、再生を始める直前に一瞬（短い区間なら数十ミリ秒）処理時間がかかる。無音audioや、Media Session の登録は倍速と無関係に今までどおり。

- 入力欄の文字サイズは16px以上にする（未満だと入力時に画面が拡大される）。

15.11 GitHub Pagesの無料運用について（依頼者の疑問への回答）

- **無料の条件**: リポジトリを Public（公開）にしておくこと。Private にすると、Pagesの利用に有料プランが必要になる。
- **公開されるもの**: リポジトリの中身は誰でも見られる。個人情報や音声ファイルは入れない（音声は各自のiPhoneの中にあり、サーバーを通らない）。
- **上限の目安**（GitHubの公式ドキュメントに基づく目安。条件が変わることがあるため、気になる場合は公式ページで確認する）: サイトの大きさ約1GB、通信量は月100GB程度、公開（ビルド）は1時間に10回程度。
- **KEecoloopの規模**: アプリ全体で約70KB。100GBは約140万回分のダウンロードに相当する。さらにアプリはiPhoneに保存される（サービスワーカー）ため、2回目以降の起動ではほぼ通信しない。つまり「何回使うか」ではなく「新しく使い始める人の数」で決まる。数万人規模にならない限り、上限には届かない。
- **Netlifyとの違い**: Netlifyは「クレジット」を消費し、使い切るとサイトが止まる。GitHub Pagesの通信量の上限は「目安」で、超えても自動で止まらず、GitHubから連絡が来て対応をお願いされる形。
